# Backend architecture

> Status: accepted · 2026-10-09 · Implements PLAN.md §2–4 for Phase 0/1.

## Goals

1. Replace the web prototype's localStorage data with a real API + database, without changing the screens.
2. Same API for the web app now and an Expo app later (no logic in Next.js).
3. Small enough to run on a €6 VPS or a Raspberry Pi, and identically on a laptop.
4. Ready for 2 users today (you + partner), able to grow to a coach with many athletes.

## Overview

```
 Browser / PWA ──► Next.js (apps/web) ──/api/*──► Hono API (apps/api) ──► PostgreSQL
 (later) Expo  ─────────────────────────/api/*──┘        │
                                                         └── packages/core (Zod schemas, sports, exercises)
```

- In **dev**, Next.js rewrites `/api/*` to `http://localhost:4000/*`.
- In **prod**, Caddy routes `/api/*` to the API container and everything else to the web container.
- Both cases serve web and API from **one origin**, so auth cookies are first-party: no CORS and no tokens in localStorage.

## Components

| Part | Choice | Notes |
|---|---|---|
| HTTP server | **Hono** on Node (`@hono/node-server`) | Small, fast, typed; also runs on Bun or edge runtimes if needed |
| Validation | **Zod** schemas in `packages/core` + `@hono/zod-validator` | The same schemas validate web forms and API input |
| Typed client | **`hono/client`** (`hc<AppType>`) | End-to-end types for the web app and Expo, without a codegen step. Add OpenAPI later if third parties need it |
| Auth | **Better Auth** (email + password, cookie sessions, Drizzle adapter) | Self-hosted, so data stays in our DB. Expo plugin exists for mobile. Passkeys/2FA are plugins we can add |
| DB | **PostgreSQL 16** + **Drizzle ORM** + `postgres` (postgres.js) driver | SQL-first, typed; migrations generated by drizzle-kit and applied on API start |
| Background jobs | none yet → **pg-boss** when imports/adaptation arrive | Queue in Postgres, so no Redis |
| Config | env vars validated by Zod at startup (`apps/api/src/env.ts`) | Fails fast on bad config |
| Tests | **Vitest** against a real Postgres (docker compose) | Route-level tests via `app.request()` |

## Layering (inside `apps/api`)

```
routes/*.ts      HTTP only: parse + validate input, call service, shape response
services/*.ts    business rules + authorization (policy) — no HTTP types
db/              Drizzle schema, client, migrations, seed   (packages/db later if the worker needs it)
policy.ts        canAccess(user, athleteId, action) — the one place permissions are decided
```

Rules:
- Every route that touches athlete data calls `requireAthlete(c, athleteId, 'read'|'write')`.
- Services take plain arguments (`userId`, `athleteId`, DTOs) and are reusable from the worker and from LLM tools later.
- Request and response bodies are Zod types from `@tc/core`, never Drizzle rows leaking out.

## Access model: users vs athletes

A **user** is someone who logs in. An **athlete** is someone who trains and has a plan. They are separate:

```
user ──< athlete_access >── athlete
          role: owner | coach | viewer
```

- On sign-up, a user gets their own athlete profile (`owner`).
- **Household / partner:** each grants the other `coach` (edit) or `viewer` (read) access, and the profile switcher shows every athlete you can access.
- **Coach with many athletes:** the same table, so no schema change is needed.
- **Athletes without login** (e.g. a child): an athlete row with only a `coach`/`owner` link from the parent.

## Data model (v1)

```
user, session, account, verification     ← Better Auth tables
athlete            id, name, initials, color, goal, goal_date, rec_note, created_by
athlete_access     user_id, athlete_id, role                         PK(user_id, athlete_id)
sport              id ('run'…), label, color, description, endurance  ← seeded from @tc/core
athlete_sport      athlete_id, sport_id
exercise           id, name, group, equipment, level, muscles, cue, default_sets/reps/load, owner_id NULL=global
athlete_exercise_rec  athlete_id, exercise_id, position           ("For you")
planned_session    id, athlete_id, date, time, duration_min, sport_id, title, note,
                   source (coach|me|past), repeated_from, coach_note,
                   distance_m, target, completed_at, rpe, feeling, created_by
session_exercise   id, session_id, position, exercise_id, sets, reps, load, done_at
suggestion         id, athlete_id, title, sport_id, duration_min, why, exercises JSONB  ← "Ask my coach"
device_connection  athlete_id, provider, connected, import_activities, push_workouts, last_sync_at
```

Notes:
- Dates are `date` and times are `time` columns (the athlete's local wall-clock time), because training plans are calendar-based, not instant-based.
- Distances are stored in meters (SI). The UI formats them.
- `completed_at` on a session plus `done_at` on each exercise replace the prototype's `completed`/`doneExercises` maps.
- Activities from devices/FIT files (`activity`, `activity_stream`) and load metrics (`daily_load`) arrive with Phase 2 and are not created yet.

## API (v1)

All routes are under `/api`. Auth uses the Better Auth cookie.

```
POST /api/auth/*                                  Better Auth (sign-up, sign-in, sign-out, session)
GET  /api/v1/me                                   user + accessible athletes (with role)
GET  /api/v1/catalog                              sports + exercises
GET  /api/v1/athletes/:aid                        profile, sports, recommendations, goal, current thresholds
PATCH /api/v1/athletes/:aid                      name, goal, goal date, thresholds (SI units; changes start a history entry)
GET  /api/v1/athletes/:aid/thresholds             threshold history (newest first)
PUT  /api/v1/athletes/:aid/sports                 set active sports
GET  /api/v1/athletes/:aid/sessions?from&to       planned sessions with exercises
POST /api/v1/athletes/:aid/sessions               create (builder "Save training")
PATCH /api/v1/sessions/:sid                       move/edit/complete (completedAt, date, time, …)
DELETE /api/v1/sessions/:sid
PATCH /api/v1/sessions/:sid/exercises/:eid        toggle done
GET  /api/v1/athletes/:aid/suggestions            coach suggestions
GET  /api/v1/athletes/:aid/devices                device connections
PUT  /api/v1/athletes/:aid/devices/:provider      connect/disconnect/toggle options (simulated until partner APIs)
POST /api/v1/athletes/:aid/access                 share: give another user (by email) coach/viewer access
GET  /api/v1/athletes/:aid/integrations           Strava status (available, connected, last sync, activity count)
POST /api/v1/athletes/:aid/integrations/strava/connect   owner only → { url } of Strava's consent screen
GET  /api/v1/integrations/strava/callback         OAuth callback → stores encrypted tokens, first sync, redirects to /settings
POST /api/v1/athletes/:aid/integrations/strava/sync      import new activities (coach/owner)
DELETE /api/v1/athletes/:aid/integrations/strava  revoke at Strava + forget tokens (imported activities stay)
GET  /api/health
```

## Frontend integration

- **TanStack Query** owns server state: sessions, athletes, catalog. Mutations update optimistically, so ticking off an exercise feels instant.
- **Zustand** keeps only UI state: selected athlete, layouts, calendar month, filters, the builder draft.
- `/login` and `/signup` pages. The app shell redirects to `/login` when there's no session.

## Security

- Passwords are hashed by Better Auth (scrypt), with HTTP-only `SameSite=Lax` cookies, `Secure` in prod.
- Every athlete-scoped query goes through `policy.ts`. Tests cover "user B can't read user A's sessions".
- Auth routes are rate-limited (Better Auth built-in).
- No health data in logs: the request logger prints method, path, status and duration only.
- Integration OAuth tokens are encrypted with AES-256-GCM (`src/crypto.ts`), key derived via HKDF from `BETTER_AUTH_SECRET`. OAuth `state` is HMAC-signed, bound to user + athlete, valid 10 minutes, and authorization is checked before tokens are stored.

## Activity import (Strava)

- `packages/integrations` implements the read-only `ActivitySource` port for Strava (scope `read,activity:read_all`) and maps Strava activities to SI units. Unsupported sports (swim, walk, …) are skipped.
- Imported activities live in `activity` (unique per provider + external id, so re-syncs are idempotent). Each is linked to the planned session it fulfilled: same day and sport, not yet linked, closest start time; that session is marked complete. An activity with no plan becomes a session with source `import` ("Logged").
- Sync currently runs in the request (on connect and "Sync now"); that is fine for a handful of users. At go-live it moves to Strava webhooks + `apps/worker` (pg-boss), as the architecture rules require for background work.

## Deployment shape

```
docker-compose.prod.yml:  caddy (443) → web:3000, api:4000 → postgres:5432 (volume) ; nightly pg_dump → offsite
```

The same images run on a Hetzner VPS or a home server. See `docs/hosting-options.md`.
